# 레포별 즉시 동기화 요청 설계

## 목적

GitHub App을 사용하는 외부 프로젝트 팀이 운영팀 요청이나 매일 오전 9시(KST) 정기 동기화를 기다리지 않고, 권한이 있는 자기 레포 한 곳에 현재 AI Harness `main`의 동기화를 요청할 수 있게 한다.

이 기능은 [팀별 AI Harness 대시보드 설계](2026-08-12-team-dashboard-design.md)의 후속 확장이다. 설정 항목 선택·설정 PR 생성과 독립적으로 동작한다.

## 사용자 흐름

1. 대시보드에서 사용자가 관리할 레포를 연다.
2. "지금 동기화"를 요청한다.
3. 대시보드는 권한·설치 범위·설정 상태·중복 요청을 검사한다.
4. 조건을 만족하면 하네스 원본 레포의 workflow를 해당 레포 하나만 대상으로 실행한다.
5. 대시보드는 실행 URL을 보여 준다. 동기화 결과는 기존처럼 대상 레포의 sync PR과 Actions 요약에서 확인한다.

## 요청 조건

요청 전과 workflow 실행 직전에 아래 조건을 모두 확인한다.

1. OAuth 사용자가 대상 레포에 `maintain` 또는 `admin` 권한을 가진다.
2. GitHub App이 대상 레포에 설치되어 있다.
3. 대상 레포의 `.harness/sync.yml`이 유효하고 `enabled: true`다.
4. 같은 레포에 열린 동기화 PR이 없다.
5. 같은 레포에서 최근 10분 이내에 즉시 동기화를 요청하지 않았다.
6. 같은 레포의 즉시 동기화 실행이 진행 중이거나 대기 중이지 않다.

`enabled: false`인 레포는 먼저 설정 PR을 병합해 활성화해야 요청할 수 있다.

## 실행 구조

대시보드는 하네스 원본 레포의 `workflow_dispatch`를 호출한다. 워크플로에는 필수 입력 `target_repo`를 추가한다.

`scripts/list-installed-repos.py`는 `target_repo`가 주어지면 그 이름과 정확히 일치하는 App 설치 레포만 동기화 매트릭스에 넣는다. 대상이 발견되지 않으면 실패한다. 이 검증으로 사용자가 App 설치 범위 밖 또는 다른 레포를 실행 대상으로 만들 수 없다.

워크플로는 `target_repo`를 포함한 동시성 그룹을 사용해 같은 레포의 요청을 직렬화한다. 서로 다른 레포의 요청은 독립적으로 실행한다.

대시보드 서버는 하네스 원본 레포에 설치된 GitHub App 설치 토큰으로만 workflow dispatch를 요청한다. 해당 설치에는 원본 레포의 Actions workflow 실행 권한이 필요하다.

## 호출 제한과 중복 처리

대시보드는 레포별 요청 시각을 10분간 보관한다. 이 단기 상태에는 레포 식별자와 요청 시각만 저장하고, 프로젝트의 스킬 선택이나 동기화 설정은 저장하지 않는다.

- 열린 동기화 PR이 있으면 실행을 만들지 않고 해당 PR URL을 반환한다.
- 쿨다운 중이면 다음 요청 가능 시각을 반환한다.
- 실행 중이거나 대기 중이면 해당 workflow 실행 URL을 반환한다.

## 오류 처리

다음 오류를 구분해 표시한다.

- 대상 레포 권한 부족
- GitHub App 미설치 또는 설치 범위 밖
- 동기화 비활성화 또는 YAML 설정 오류
- 열린 동기화 PR 존재
- 10분 쿨다운 또는 실행 중복
- workflow 실행 권한 부족 또는 dispatch 실패
- `target_repo`가 설치 레포 목록에 없음

## 검증

- `target_repo` 입력이 App 설치 범위의 한 레포만 동기화 매트릭스에 넣는지 검증한다.
- 권한 부족, 비활성 설정, 열린 동기화 PR, 10분 쿨다운, 진행 중 실행이 요청을 차단하는지 GitHub API mock으로 검증한다.
- 같은 레포의 동시 요청이 하나의 workflow 실행만 만들고, 서로 다른 레포 요청은 독립적으로 실행되는지 검증한다.
- GitHub 테스트 레포에서 즉시 동기화 요청부터 해당 레포 하나에만 sync PR이 생성되는지 검증한다.
