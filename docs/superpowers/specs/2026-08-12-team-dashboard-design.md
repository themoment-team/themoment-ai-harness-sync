# 팀별 AI Harness 대시보드 설계

## 목적

각 프로젝트 팀이 YAML을 직접 수정하지 않고 웹에서 AI Harness 동기화 항목을 선택하고, 검토 가능한 설정 PR로 `.harness/sync.yml`을 변경한다.

## 범위

- Claude/Codex 스킬·에이전트, opt-in 훅, 설정 파일, Gemini 설정을 선택한다.
- 레포별 동기화 활성화/비활성화를 설정한다.
- 선택 결과와 현재 설정의 YAML diff를 보여 주고 설정 PR을 만든다.
- 기존 `sync-manifest.yml`, GitHub Actions 동기화 워크플로, GitHub App 기반 파일 배포를 재사용한다.
- 권한이 있는 팀원이 특정 레포의 동기화를 즉시 요청할 수 있다.

다음은 범위에서 제외한다: 동기화 PR 병합, 조직 관리, 사용 통계, 별도 구성 DB.

## 구성

별도 Next.js 대시보드를 배포한다.

- **대시보드**: GitHub 로그인, 접근 가능한 레포 목록, 항목 선택, 설정 diff 표시, PR 생성.
- **GitHub OAuth App**: 사용자 로그인 세션과 레포 권한 확인.
- **기존 GitHub App**: 설치된 레포 범위 확인 및 설정 브랜치·커밋·PR 생성용 설치 토큰 발급.
- **이 저장소**: `sync-manifest.yml`을 배포 가능 항목의 단일 원천으로 유지.
- **대상 레포**: `.harness/sync.yml`만 팀별 구성의 저장소로 사용.

대시보드는 선택 상태를 데이터베이스에 복제하지 않는다. 매 요청마다 하네스 `main`의 매니페스트와 대상 레포의 실제 설정을 읽는다. 즉시 동기화의 쿨다운만 짧은 수명의 상태 저장소에 보관한다.

## 권한

사용자는 GitHub OAuth로 로그인한다. PR을 만들기 직전에 서버는 다음을 모두 확인한다.

1. 사용자가 대상 레포에 `maintain` 또는 `admin` 권한을 가진다.
2. 기존 GitHub App이 대상 레포에 설치되어 있다.

OAuth 토큰은 로그인과 사용자 권한 확인에만 쓴다. 브랜치·파일·PR 변경은 GitHub App 설치 토큰으로만 수행한다. OAuth client secret, GitHub App private key, 세션 암호화 키만 서버 비밀값으로 보관한다.

## 화면과 사용자 흐름

1. 사용자는 로그인 후 권한과 App 설치 범위를 모두 만족하는 레포만 본다.
2. 레포를 선택하면 현재 `.harness/sync.yml`과 해석된 동기화 항목을 표시한다.
3. 사용자는 Claude, Codex, Gemini 그룹과 스킬·에이전트·훅·설정 파일의 개별 선택을 변경한다.
4. 사용자는 `enabled` 토글로 동기화를 시작하거나 멈춘다. 토글은 선택한 항목을 지우지 않는다.
5. 화면은 생성될 YAML과 현재 설정의 diff를 보여 준다.
6. 사용자가 확정하면 설정 PR을 만들고 PR URL로 이동한다.

## 설정 정책

### 새 대시보드 구성

새 구성은 미래 항목을 자동 수신하지 않는 고정 allow-list를 기본으로 한다.

```yaml
enabled: true
groups: []
overrides:
  claude/skills/api-design: true
  claude/agents/web-researcher: true
  codex/skills/api-design: true
  gemini/settings: true
```

따라서 하네스 `main`에 새 항목이 추가되어도, 해당 항목을 선택하지 않은 레포에는 동기화 PR이 생기지 않는다. 사용자는 원하면 그룹 기반 자동 수신 모드로 전환할 수 있다.

### 기존 레포

기존 `groups` 기반 구성은 변경하지 않는다. 대시보드는 이 상태를 "새 항목 자동 수신"으로 표시한다. 팀이 명시적으로 "고정 선택으로 전환"을 선택할 때만 현재 수신 항목을 `groups: []`와 개별 `overrides`로 변환한다.

### 동기화 활성화

`enabled: false`는 대상 레포를 동기화 매트릭스에서 완전히 제외한다. 새 스킬·에이전트 동기화 PR과 고아 파일 정리 PR 모두 생성되지 않는다. 다시 활성화해도 기존 선택 구성은 보존된다.

`.harness/sync.yml`이 없는 설치 레포의 현행 기본 동작은 유지한다. 즉 기존 레포에 대해 설정 파일 부재를 비활성으로 해석하지 않는다.

## PR 생성

서버는 대상 레포의 설정된 `base_branch`에서 `harness-config/<timestamp>` 브랜치를 만든다. `.harness/sync.yml`만 변경해 커밋하고, 선택 요약·YAML diff·작성자를 포함한 PR을 생성한다.

동일 레포에 열린 `harness-config/` 설정 PR이 있으면 새 PR을 만들지 않고 그 PR URL을 반환한다. 사용자는 기존 PR을 검토·병합 또는 종료한 후 새 변경을 만든다.

설정 PR이 병합된 뒤에만 현행 동기화 워크플로가 변경된 설정을 읽는다.

## 즉시 동기화 요청

대시보드는 각 레포 화면에 "지금 동기화" 버튼을 제공한다. 이는 설정 변경과 별개이며, 외부 팀이 운영팀 요청이나 정기 실행을 기다리지 않고 현재 하네스 `main`의 내용을 자기 레포 하나에 반영하도록 요청하는 기능이다.

요청 전과 실행 직전에 다음을 확인한다.

1. OAuth 사용자가 대상 레포에 `maintain` 또는 `admin` 권한을 가진다.
2. GitHub App이 대상 레포에 설치되어 있다.
3. 대상 레포의 `.harness/sync.yml`이 유효하고 `enabled: true`다.
4. 같은 레포에 열린 동기화 PR이 없다.
5. 같은 레포에서 최근 10분 이내에 즉시 동기화를 요청하지 않았다.
6. 같은 레포의 즉시 동기화 실행이 진행 중이거나 대기 중이지 않다.

조건을 만족하면 대시보드는 하네스 저장소의 `workflow_dispatch`를 호출한다. 워크플로에는 필수 입력 `target_repo`를 추가하고, `scripts/list-installed-repos.py`는 이 값과 정확히 일치하는 App 설치 레포만 매트릭스에 넣는다. 사용자가 임의의 레포를 실행 대상으로 바꾸지 못하도록 워크플로도 `target_repo` 형식을 검증하고, 발견한 App 설치 범위 밖 레포는 실패 처리한다.

워크플로는 `target_repo`를 포함한 동시성 그룹을 사용해 같은 레포의 즉시 요청을 직렬화한다. 대시보드는 레포별 쿨다운 기록을 10분간 보관한다. 이 상태 저장소는 요청 시각과 레포 식별자만 보관하며, 스킬 선택이나 대상 레포 설정을 저장하지 않는다.

열린 동기화 PR이 있으면 실행을 새로 시작하지 않고 그 PR URL을 반환한다. 쿨다운 또는 진행 중 실행이면 다음 허용 시각 또는 현재 실행 URL을 반환한다. `enabled: false`인 레포는 먼저 설정 PR을 병합해 활성화해야 즉시 동기화를 요청할 수 있다.

이 호출을 위해 대시보드 서버는 하네스 원본 레포에 설치된 GitHub App 설치 토큰으로만 `workflow_dispatch`를 요청한다. 해당 App 설치에는 하네스 원본 레포의 Actions workflow 실행 권한이 필요하다.

## 오류 처리

다음 오류는 구분해 표시한다.

- 대상 레포 권한 부족
- GitHub App 미설치 또는 설치 범위 밖
- 설정된 기준 브랜치 없음
- 열린 설정 PR 존재
- 대상 레포의 YAML 구문 오류
- 선택한 매니페스트 항목이 더 이상 존재하지 않음
- 동기화 비활성화 상태
- 열린 동기화 PR 존재
- 즉시 요청 쿨다운 또는 실행 중복
- 즉시 동기화 workflow 실행 권한 또는 실행 요청 실패

YAML이 비정상인 경우 대시보드는 자동으로 덮어쓰지 않고 오류와 수동 수정 안내만 제공한다.

## 검증

- 매니페스트와 선택 상태에서 `sync.yml`을 만드는 규칙을 단위 테스트한다.
- 고정 allow-list가 새 매니페스트 항목을 자동 선택하지 않는지 검증한다.
- `enabled: false` 생성과 해석을 검증한다.
- OAuth 권한 부족, App 미설치, 열린 설정 PR, 기준 브랜치 부재를 GitHub API mock으로 검증한다.
- `target_repo` 입력이 해당 App 설치 범위의 한 레포만 동기화 매트릭스에 넣는지 검증한다.
- 권한 부족, 비활성 설정, 열린 동기화 PR, 10분 쿨다운, 진행 중 실행이 즉시 동기화를 차단하는지 검증한다.
- 같은 레포의 동시 즉시 요청이 하나의 workflow 실행만 만들고, 서로 다른 레포 요청은 독립적으로 실행되는지 검증한다.
- 실제 GitHub 테스트 레포에서 OAuth 로그인부터 설정 PR 생성, PR 병합 후 동기화 워크플로 적용까지 한 번 검증한다.
- 실제 GitHub 테스트 레포에서 즉시 동기화 요청부터 레포 하나에만 sync PR이 생성되는지 검증한다.
